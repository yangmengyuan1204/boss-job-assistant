5. 去重策略

derive_job_id() 推导优先级：

  1. job_url 路径末段：如 /job_detail/abc123.html → abc123（去除 .html / .htm 后缀）

P3.1-4. 三态 UPSERT 设计

P3 原实现中 UPSERT 无法区分"更新"和"重复"，导致重复数量永远为 0。P3.1 引入 UpsertOutcome 枚举与 BulkUpsertResult 模型。

UpsertOutcome 三态：

状态含义
NEW数据库中不存在该 job_id
UPDATED已存在且业务字段变化
UNCHANGED已存在且业务字段全部相同（重复）

BulkUpsertResult：

BulkUpsertResult(
    new_count: int,
    updated_count: int,
    unchanged_count: int,
)
# total = new + updated + unchanged == len(records)

P3.1-5. NEW / UPDATED / UNCHANGED 判断规则

业务字段（参与变化判断）： title, salary, company, location, experience, education, job_url, company_url, page_no。

条件结果
数据库中不存在相同 job_idNEW
存在相同 job_id 且业务字段任一变化UPDATED
存在相同 job_id 且业务字段全部相同UNCHANGED

规范化规则： None 与空字符串 "" 统一视为 None 比较，避免 NULL 与空串差异导致误判 UPDATED。

P3.1-6. collected_at 处理语义

collected_at 不参与业务字段变化判断，仅 collected_at 变化时结果为 UNCHANGED 而非 UPDATED。

UPSERT 时 collected_at 总是被更新为本次采集时间（即使 UNCHANGED），以便跟踪最后一次访问时间。但统计结果仍为 UNCHANGED。

P3.1-7. 同批次重复 job_id 处理方式

bulk_upsert_job_list 按顺序逐条调用 save_job_list，每条以之前写入后的数据库行为基线比较。

示例： 同批次 3 条 job_id="dup"：

  1. title="v1" → NEW（DB 无记录）
  2. title="v2" → UPDATED（DB 为 v1，title 变化）
  3. title="v2" → UNCHANGED（DB 已为 v2，业务字段全同）

结果： new=1, updated=1, unchanged=1, total=3（不超过输入记录数）。整个批量处理位于同一事务中，不为每条记录创建独立连接。

P3.1-8. URL 二次防御说明

P3.1 在 JobListRecord.from_observed_card() 转换边界再次调用 sanitize_url()，形成防御性校验，不信任调用者一定已经脱敏。

防御规则：

  • query 被剥离（返回无 query 的干净 URL）
  • fragment 被剥离（返回无 fragment 的干净 URL）
  • userinfo URL 被拒绝（返回 None）
  • 显式端口 URL 被拒绝（返回 None）
  • HTTP URL 被拒绝（不自动升级，返回 None）
  • 非 BOSS 官方域名被拒绝（返回 None）

同时覆盖 job_url 与 company_url。

P3.1-9. 异常隔离

以下异常不导致命令循环崩溃，仅输出安全错误类型（不含异常原文），写入脱敏日志后返回命令循环：

  • Parser 异常 → "解析器异常"
  • Diagnostics 处理异常 → 使用空摘要继续
  • Pydantic 模型转换异常 → "模型转换异常"
  • SQLite 写入异常 → "数据库写入异常"
  • 日志写入异常 → 仅 logger.warning，不崩溃

禁止输出：完整页面 HTML、敏感 URL、数据库完整内容、异常对象中可能包含的页面原文。异常消息不输出到终端或日志。
