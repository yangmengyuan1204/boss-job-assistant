3. CLI 非阻塞退出设计

3.1 设计目标

  • 用户在终端等待输入期间关闭浏览器 → CLI 立即结束，无需用户再次按回车
  • 唯一页面关闭 → 立即退出
  • context 关闭 → 立即退出
  • 输入线程必须为 daemon，不阻止进程结束
  • 不强制终止线程，不引入复杂异步框架
  • Ctrl+C 仍能安全退出
  • 单元测试不真正读取终端

3.2 架构：CommandSource 协议 + daemon 输入线程

定义可注入接口：

class CommandSource(Protocol):
    def start(self) -> None: ...
    def poll(self, timeout: float) -> str | None: ...
    def stop(self) -> None: ...

生产实现 ThreadedCommandSource：

  • 输入线程：daemon 线程，name=boss-tool-cmd-reader，循环调用 input_func(prompt) 并把结果放入 queue.Queue
  • 主线程：在 _run_command_loop 中循环轮询三件事：
    1. manager.is_running（浏览器/context 是否还在）
    2. session.state.is_terminal()（session 是否终态）
    3. command_source.poll(poll_interval)（命令队列，超时即返回 None）
  • 任意一项满足即立即返回，无需用户输入
  • stop() 仅标记状态并向队列放入 None 唤醒，不调用 thread.join()，不强制终止线程

3.3 主循环关键逻辑

while True:
    # 1. 浏览器已关闭 → 立即退出（无需输入）
    if not manager.is_running:
        typer.echo("[INFO] 浏览器已关闭（由用户或异常触发），会话结束。")
        return
    # 2. session 已终态 → 立即退出
    if session.state.is_terminal():
        typer.echo("[INFO] 会话已结束。")
        return
    # 3. 非阻塞轮询命令（poll_interval 秒超时即返回 None）
    cmd = command_source.poll(timeout=poll_interval)
    if cmd is None:
        continue  # 无命令，继续检查浏览器状态
    # ... 处理 confirm / quit / status

3.4 测试可注入

测试通过 FakeCommandSource 预置命令队列直接注入 _run_command_loop(command_source=...)，不通过 CliRunner input=，不读取真实终端。

3.5 修复记录：测试 hang 问题

P1.1 验证过程中发现的额外问题：

初版 FakeCommandSource.poll() 在 start() 未调用时直接返回 None，导致主循环因 manager.is_running=True 且命令源持续返回 None 而无限轮询。

修复： poll() 不再依赖 _started 标志，_started 仅用于协议一致性。修复后 244 个测试全部通过。

4. URL 统一校验规则

4.1 统一入口

新增公共函数 validate_home_url(url: str) -> str（位于 src/boss_tool/browser/manager.py），Pydantic、CLI 覆盖参数、BrowserManager 均调用同一套逻辑，消除 config.py / cli.py / manager.py 三处重复校验。

4.2 严格规则

#规则拒绝示例
1scheme 必须严格等于 httpshttp://www.zhipin.com/
2hostname 必须严格属于 {"www.zhipin.com", "zhipin.com"}https://www.zhipin.com.evil.com/
3禁止 parsed.usernamehttps://user@www.zhipin.com/
4禁止 parsed.passwordhttps://user:pass@www.zhipin.com/
5禁止显式非默认端口（parsed.port is not None）https://www.zhipin.com:8443/
6禁止 fragmenthttps://www.zhipin.com/#fragment
7禁止 query（防止携带 token 等敏感参数）https://www.zhipin.com/?token=secret
8首页路径限制为 / 或空https://www.zhipin.com/job/123

4.3 允许的 URL

https://www.zhipin.com/
https://zhipin.com/

4.4 恶意相似域名防护

urlparse 的 hostname 会自动去掉端口与 userinfo，但对 evil.com@www.zhipin.com 这类 userinfo 注入，规则 3/4 直接拒绝；对 www.zhipin.com.evil.com 这类相似域名，规则 2（hostname 不在白名单）直接拒绝。

4.5 错误信息脱敏

所有 ValueError 错误信息仅引用 redact_url(url) 的脱敏形式，不出现 query 参数原值。已通过 test_error_message_does_not_contain_token 验证：错误信息中不含 supersecret。

4.6 CLI 输出脱敏

原代码 typer.echo(f"首页: {effective_home_url}") 改为：

typer.echo(f"首页:     {redact_url(effective_home_url)}")

日志同样使用脱敏 URL，不输出未经脱敏的 URL。

5. 关闭来源语义

5.1 问题

原代码 context/page 只要不是 manager 主动关闭就全部标记 browser_closed_by_user=True，无法区分用户主动关闭与异常断开。

5.2 新增 CloseSource 枚举

class CloseSource(str, Enum):
    MANAGER = "manager"              # BrowserManager.close() 主动调用
    PAGE = "page"                    # 明确收到 page "close" 事件
    CONTEXT = "context"              # context 关闭但此前无 page close 证据
    STARTUP_FAILURE = "startup_failure"  # 启动阶段失败
    UNKNOWN = "unknown"              # 未知来源

5.3 判定规则

触发场景close_sourcebrowser_closed_by_userstop_reason
manager 主动调用 close()managerFalse调用方传入（如 USER_ABORTED）
page 收到 close 事件pageTrueBROWSER_CLOSED
context 收到 close 事件，且此前已观察到 page closepage（级联）TrueBROWSER_CLOSED
context 收到 close 事件，但此前未观察到 page closecontextFalseBROWSER_CONTEXT_CLOSED（中性，不声称为用户行为）
启动阶段失败startup_failureFalseUNKNOWN_ERROR

5.4 实现要点

  • 新增 self._page_close_observed = False 标志，page close 事件触发时置为 True
  • context close 处理器检查该标志：若 True 则视为 page 级联，否则视为来源不确定
  • 不伪造"用户关闭"：context 来源时 browser_closed_by_user=False，stop_reason=BROWSER_CONTEXT_CLOSED
  • 新增 StopReason.BROWSER_CONTEXT_CLOSED = "browser_context_closed" 中性描述
  • 幂等：终态会话不再触发状态迁移（session.state.is_terminal() 检查）

5.5 数据模型兼容性

close_source 字段为可选（CloseSource | None），向后兼容；旧数据 close_source=None 不受影响。

10.1 black 检查（环境限制）

如实记录： 本环境运行 python -m black --check . 持续挂起（即便单文件 black --check src/boss_tool/browser/commands.py 也无法在 60 秒内返回），属于环境问题，非伪造结果。

按用户要求"如black可用，再执行；不得伪造black结果"，black 在该环境不可用，故以 ruff format --check（与 black 格式化标准一致）作为格式化验证依据。

后续若在 black 可用的环境中运行，建议执行 python -m black --check src tests 复核。
